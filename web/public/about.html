HTB26 · a research tool with receipts

Answers you can take apart.

Dashboards and AI assistants hand you a number, but you can't see how it was made or check where it came from. In Backtrace you ask a question in plain English, agree with Claude on the shape of the answer, and get a result where every number traces back to the raw rows behind it.

When the answer changes over time, Backtrace offers to look into the future. The next value becomes an open question on an information exchange: people who know more move the odds, and everyone else gets a sharper view of what comes next. When the data is published, the same calculation settles it.

The pitch

A number is only as good as its working.

The problem

Spreadsheets hide the working in cells, dashboards hide it in pipelines, and chat assistants hide it inside a model. To check an answer you have to rebuild it yourself, so most answers go unchecked.

What Backtrace does

It builds every answer as a chain of small, approved steps from public source data to the result. Claude proposes each step, and you approve, edit or comment. Every step is kept, so any number opens back up into the rows it came from.

Why it matters

An answer that anyone can re-compute and check can be relied on by other people and other systems. That makes it a fair question to ask about the future: an exchange can commit to the exact calculation today, let people with better information move the odds, and settle on it when new data arrives.

The journey

Start with a question, not a dataset.

One question is one thread. The chat floats beside a canvas that fills up as you go: the question, the tables that answer it, and the data they came from. The running example is "Will the flat market in Reading grow next year?"

  1. Ask

    Sharpen the question

    Claude restates it as parts you can edit: flats, Reading, median price, by year, year on year.

  2. Shape

    Agree the shape of the answer

    Columns, units, what one row means and the scope, with preview rows, so you see the table before any data exists.

  3. Data

    Find and load the data

    Claude works backwards from the answer to the data it needs, offers public datasets as cards, and loads the one you pick.

  4. Answer

    Evaluate and trace

    The chain runs, the table fills with real numbers and a verified fingerprint, and any value opens its receipt.

  5. Future

    Look into the future

    For a time series, the next period appears as an empty row. Open that cell as a question and watch the odds form.

Each step is a proposal you approve, edit or discard. Turn on auto-accept to go straight to the answer and inspect the path afterwards. Follow-ups such as "by postcode district" become new tables in the same workspace, reusing what's already there.

The model

One graph, three directions.

Everything lives on one graph. A view is a table definition: its shape plus the transform that computes it. There is no final view, only views connected to each other. From any approved view you can go upstream, downstream, or to a visual.

View
A table definition: its shape plus the transform that computes it. A raw dataset is a source view.
Shape
JSON Schema for one row with roles and units, plus the grain (what one row is) and the scope, e.g. "Reading, flats, 2023–2025".
Transform
Deterministic (filter, derive, aggregate, or Python) or agentic (Claude classifies, infers or summarises, with schemas as structured input and output).
Visual
HTML written by the agent that renders a view, in a sandboxed floating window. Click a point to trace it.
Instance
One evaluation of a view. It pins the exact shape, transform and input instances it used.
Record
One row of an instance, linked to the source rows it came from.

Append-only versioning

Proposals are never edited. A revision is a new node that points at its parent, and alternatives are siblings. Each approval increments a global counter, and the approved version with the highest counter is current. Discarded proposals stay on the graph, so you can replay the reasoning next to the data lineage.

Receipts

Every number has a receipt.

Two things make an answer checkable: lineage, which says where each number came from, and fingerprints, which prove nothing changed along the way.

Lineage down to the raw rows

Every output row carries _src, the ids of the rows it was made from. Trace walks back one level at a time, from a value to the sales behind it to the raw Land Registry records.

Fingerprints for the whole chain

Each table's fingerprint covers its formula, a Merkle root of its rows and the fingerprints of its inputs. The final table's fingerprint therefore commits to every step down to the source files.

Verify re-runs it

Verify recomputes the chain from the stored inputs and compares every hash, then shows the tree. A notebook view lays out each step as readable pandas code, and the chain exports as a script that rebuilds the result from the source CSVs.

AI steps are marked

An agentic step can be replayed but not recomputed, so it is fingerprinted by its stored output and flagged in the verify report. Questions about the future can't be built on chains with AI steps.

Example hashes. Rows are hashed in canonical form: sorted keys, fixed float rounding, ISO dates.

The hashes prove the computation is faithful to the data. They don't prove the publisher's data is authentic; anyone can re-download the source file and compare its sha256.

Information exchange

Would you like to look into the future?

The future can be defined as precisely as the past. The empty 2026 row will be filled by exactly the same calculation as the rows above. Until then it is an open question: anyone who knows something about it can back their view, and the odds show everyone what the best-informed people expect.

  1. The empty row

    The data stops here

    A time series gains a next-period row with a value of "?". A simple trend line shows what a naive guess looks like.

  2. Ask

    A question about one cell

    The target row and column, a condition such as "at least the 2025 median", an end date, and the pinned formula it commits to.

  3. Exchange

    Information moves the odds

    People who know more, such as a local estate agent or an analyst, back YES or NO. Each position moves the odds, so the live probability becomes everyone's best estimate. It runs on Solana with test tokens.

  4. Settle

    Settled by data

    After the end date the api re-runs the pinned chain on the latest data, verifies it, compares with the line and resolves with the evidence.

The odds are worth reading. Being right pays and being wrong costs, so the odds lean toward whoever has the better information. Insight that isn't in the data yet shows up in the price.

Only fixed calculations can back a question. Every step from the sources must be approved and deterministic. An AI step blocks creation, because its output can't be recomputed.

Open questions stay pinned. Revising the view later changes what you explore, not what an open question settles on. No row at settlement means it is void.

The evidence is published. Settlement posts the value, the row, the instance fingerprint and the source files with the outcome, so anyone can recompute it.

Backtrace owns

  • What a question is about: the view, row, column and line
  • The pinned calculation and its formula hash
  • Whether and how it resolved, with the evidence

Solana owns

  • The exchange itself: YES and NO order books (OpenBook v2)
  • Collateral: complete YES + NO sets backed by mUSDC test tokens
  • Payout to whoever was right; a void question pays 0.5
Backtrace never moves funds, and the chain never computes data.
Architecture

Small services, one source of truth.

The graph is the only state. One api exposes every operation to both Claude and the browser, rows live in Postgres, and the market runs on its own Rust backend and Solana. Everything ships as one Docker Compose stack.

The graph is the only state

Chat messages, dataset choices and market drafts are graph nodes too, so the web UI, MCP clients and the terminal all see the same thread. The agent re-reads the graph every turn instead of trusting its memory.

One registry, two interfaces

Claude and the browser call the same operations. Anything the agent can do, the UI can do, and the reverse.

The agent proposes, you decide

Nothing becomes current without approval unless auto-accept is on. Every proposal carries a one-line rationale the UI shows.

Control plane and data plane

Memgraph keeps definitions, decisions and hashes. Postgres keeps the rows, where a trigger rejects updates and deletes on raw data.

Deterministic where it counts

Declarative ops can be replayed exactly. Agentic steps are stored and marked, and are kept out of anything a market settles on.

Easy to run

Docker Compose locally. In production, the same stack with overrides on one VPS: Caddy for HTTPS and the access code, hosted Postgres, and Solana devnet.
